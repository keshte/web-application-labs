# Практична робота № 6
## Тема: Валідація вхідних даних та обробка запитів у NestJS

**Дисципліна:** Розробка web-застосувань  
**Варіант:** 4 (Доставка їжі та ресторанів — ендпоінт /dishes)  
**Рівень виконання:** Рівень 3 (Просунутий — максимальний бал)  

---

## 1. Мета роботи
- Опанувати концепцію конвеєра обробки HTTP-запитів у NestJS (Request Pipeline) та послідовність виконання його елементів: `Middleware` $\rightarrow$ `Guards` $\rightarrow$ `Interceptors` $\rightarrow$ `Pipes` $\rightarrow$ `Route Handler` $\rightarrow$ `Exception Filters`.
- Навчитися реалізовувати декларативну валідацію вхідних тіл запитів (DTO) та параметрів за допомогою бібліотек `class-validator` і `class-transformer`.
- Налаштувати глобальний `ValidationPipe` із захисними механізмами фільтрації корисного навантаження (`whitelist`, `forbidNonWhitelisted`, `transform`).
- Створити власний пайп санітизації тексту (`TrimPipe`) для очищення зайвих пробілів на початку та в кінці рядкових полів.
- Створити проміжний обробник (`HttpLoggingMiddleware`) для наскрізного логування HTTP-трафіку та зареєструвати його через інтерфейс `NestModule`.
- Реалізувати кастомний фільтр виключень (`GlobalExceptionFilter`) для уніфікації формату відповідей на помилки та інтерцептор (`TimingInterceptor`) для моніторингу затримок запитів (latency) із додаванням заголовка `X-Response-Time`.

## 2. Предметна специфікація варіанта № 4

- **Категорія:** Доставка їжі та ресторанів
- **Базовий префікс маршруту:** `/dishes`
- **Модельована сутність:** `DishEntity`
- **Поля та валідаційні обмеження для `CreateDishDto`:**
  - `title`: `@IsString()`, `@IsNotEmpty()` — назва страви не може бути порожньою;
  - `price`: `@IsNumber()`, `@IsPositive()` — ціна має бути додатним числом;
  - `weightGrams`: `@IsNumber()`, `@Min(10)` — мінімальна вага порції 10 грамів;
  - `calories`: `@IsNumber()`, `@Min(0)` — невід'ємна калорійність;
  - `isSpicy`: `@IsBoolean()` — булева ознака гостроти страви;
- **Для `UpdateDishDto`:** усі поля позначені декоратором `@IsOptional()` зі збереженням відповідних типів і обмежень.

## 3. Архітектура конвеєра Request Pipeline

Конвеєр обробки кожного вхідного HTTP-запиту в NestJS проходить суворо визначений ланцюжок:

```text
Вхідний HTTP-запит
  │
  ▼
[ 1. HttpLoggingMiddleware ] ──► Фіксує час початку, метод, URL, IP клієнта
  │
  ▼
[ 2. TimingInterceptor (Start) ] ──► Засікає точний час роут-хендлера (performance.now)
  │
  ▼
[ 3. TrimPipe ] ───────────────► Рекурсивно очищує пробіли на початку/кінці рядків
  │
  ▼
[ 4. ValidationPipe ] ──────────► Перевіряє типи DTO, забороняє зайві поля (whitelist, forbidNonWhitelisted)
  │
  ▼
[ 5. Controller & Service ] ────► Виконує бізнес-логіку та CRUD-операції в сховищі
  │
  ▼
[ 6. TimingInterceptor (Finish)] ─► Встановлює заголовок X-Response-Time та логує [TIMING]
  │
  ▼
[ 7. GlobalExceptionFilter ] ───► У разі помилки формує уніфікований JSON-звіт із деталями
  │
  ▼
HTTP-відповідь клієнту (з логом у [HTTP] через finish подію middleware)
```

## 4. Опис реалізації за рівнями

### Рівень 1. Базовий: Підключення `class-validator` та валідація DTO
1. Встановлено бібліотеки `class-validator` та `class-transformer`.
2. У `main.ts` активовано глобальний `ValidationPipe` із жорстким режимом:
   ```typescript
   app.useGlobalPipes(
     new TrimPipe(),
     new ValidationPipe({
       whitelist: true,
       forbidNonWhitelisted: true,
       transform: true,
     }),
   );
   ```
3. Розмічено класи `CreateDishDto` та `UpdateDishDto` декораторами `@IsString`, `@IsNotEmpty`, `@IsNumber`, `@IsPositive`, `@Min(10)`, `@Min(0)`, `@IsBoolean`, `@IsOptional`.
4. Будь-яка спроба передати некоректний тип (наприклад, рядок замість числа чи від'ємне значення) автоматично відхиляється статусом `400 Bad Request`.

---

### Рівень 2. Санітизація даних через Custom Pipe та мережеве Middleware
1. **Кастомний пайп санітизації `TrimPipe`:**
   Реалізує інтерфейс `PipeTransform`. Якщо вхідне значення є рядком або об'єктом, рекурсивно обходить усі властивості та видаляє зайві пробіли на початку та в кінці (`.trim()`). Працює перед `ValidationPipe`, унеможливлюючи обхід перевірки `@IsNotEmpty()` рядком, що складається лише з пробілів (`"   "` $\rightarrow$ `""`).
2. **Мережевий проміжний обробник `HttpLoggingMiddleware`:**
   Реалізує інтерфейс `NestMiddleware`. Підписується на подію `res.on('finish', ...)` і виводить у лог системний запис:  
   `[HTTP] <METHOD> <URL> <STATUS_CODE> - <DURATION>ms [<IP>]`.  
   Зареєстровано в `AppModule` через метод `configure(consumer: MiddlewareConsumer)` для всіх маршрутів (`forRoutes('*')`).

---

### Рівень 3. Просунутий: Custom Exception Filter, Interceptor та наскрізне тестування
1. **Глобальний фільтр виключень `GlobalExceptionFilter`:**
   Перехоплює всі `HttpException` та транслює їх у єдиний уніфікований JSON-формат із полями `success: false`, `statusCode`, `timestamp`, `path`, `method`, `error`, `message`.
2. **Інтерцептор швидкодії `TimingInterceptor`:**
   За допомогою RxJS оператора `tap()` перехоплює вихідний потік, вимірює час виконання роут-хендлера, логує `[TIMING]` у консоль та додає клієнту службовий HTTP-заголовок `X-Response-Time: <Time>ms`.
3. **Наскрізне тестування конвеєра:**
   Створено файл `requests.http` та автоматизований PowerShell-скрипт `test_pipeline.ps1` для перевірки всіх захисних механізмів.

## 6. Відповіді на контрольні питання

### 1. Опишіть черговість проходження запиту крізь конвеєр NestJS Request Pipeline (від отримання мережевого сокету до генерації фінальної відповіді).
Послідовність виконання компонентів конвеєра:
1. **Middleware (Проміжні обробники):** виконуються найпершими на рівні Express (глобальні, потім модульні). Мають прямий доступ до об'єктів `req` і `res`.
2. **Guards (Гварди / Вартові):** перевіряють автентифікацію та дозволи доступу (JWT, RBAC). Вирішують, чи допускати запит далі.
3. **Interceptors (до виклику хендлера):** перехоплюють потік до виконання контролера (бенчмаркінг, кешування).
4. **Pipes (Пайпи):** валідують вхідні дані (`ValidationPipe`) та трансформують типи (`ParseIntPipe`, `TrimPipe`).
5. **Controller Route Handler:** виконання методу контролера та виклик методів сервісного шару.
6. **Interceptors (після виклику хендлера):** перехоплюють повернені дані за допомогою RxJS-потоків (мутація відповіді, додавання заголовків на кшталт `X-Response-Time`).
7. **Exception Filters (Фільтри виключень):** якщо на будь-якому етапі виникла помилка або викинуто `HttpException`, фільтр перехоплює її найостаннішим перед клієнтом та формує уніфікований JSON-звіт.

---

### 2. Яку роль відіграють опції `whitelist` та `forbidNonWhitelisted` у конфігурації глобального `ValidationPipe`? Від якого вектора кібератак вони захищають сервер?
- **`whitelist: true`**: автоматично відфільтровує (видаляє) з тіла запиту всі поля, які не описані декораторами валідації у відповідному класі DTO.
- **`forbidNonWhitelisted: true`**: замість мовчазного видалення зайвих полів, сервер негайно перериває обробку запиту і повертає статус `400 Bad Request` із повідомленням `property <name> should not exist`.
- **Захист від кібератак:** ці опції захищають бекенд від атак **Mass Assignment (Масове призначення)** та **Over-posting**. Без цього зловмисник міг би надіслати разом зі звичайними даними приховані поля на кшталт `isAdmin: true` або `role: 'SUPERADMIN'` і підвищити свої привілеї в системі.

---

### 3. Що робить опція `transform: true` у `ValidationPipe`? Чому без неї значення з `@Query()` та `@Param()` завжди залишаються рядками?
- **Причина:** протокол HTTP передає URL-параметри та рядки запиту виключно у текстовому вигляді (Plaintext). Без автотрансформації значення `@Query('limit') limit: number` у середовищі виконання завжди буде рядком `'5'` (тип `string`), що ламає строгу типізацію та математичні операції.
- **Дія `transform: true`:**
  1. Автоматично приводить вхідні примітиви до типів, зазначених у TypeScript-сигнатурі методу (`'5'` автоматично конвертується в число `5`).
  2. Перетворює простий об'єкт JavaScript на реальний екземпляр класу DTO за допомогою бібліотеки `class-transformer`.

---

### 4. У чому полягає відмінність між `Middleware` та `Interceptor` у NestJS? У яких сценаріях слід обрати кожен із них?
- **Middleware:** є низькорівневим інструментом платформи Express/Fastify. Виконується до того, як NestJS визначив конкретний обробник роуту. Не має доступу до контексту виконання NestJS (`ExecutionContext`), рефлексії та метаданих декораторів.
  - *Сценарії:* загальне логування HTTP-трафіку, налаштування CORS, стиснення gzip, парсинг специфічних тіл запитів.
- **Interceptor:** працює всередині екосистеми NestJS навколо виклику конкретного методу контролера. Має доступ до `ExecutionContext`, може зчитувати метадані методів, маніпулювати вхідним потоком до виклику і вихідним результатом через RxJS-оператори після завершення.
  - *Сценарії:* замір точного часу виконання роуту, кешування відповідей, глобальна серіалізація та маскування чутливих даних (видалення паролів перед відправкою).

---

### 5. Для чого призначений інтерфейс `PipeTransform`? Які аргументи приймає метод `transform(value, metadata)`?
- **Призначення:** інтерфейс `PipeTransform<T, R>` визначає контракт пайпа для **трансформації** (зміни формату/типу) або **валідації** вхідних параметрів запиту перед тим, як вони потраплять у метод контролера.
- **Аргументи методу `transform`:**
  - `value`: поточне значення параметра запиту (тіло, рядок запиту або параметр шляху).
  - `metadata`: об'єкт метаданих типу `ArgumentMetadata`, що містить:
    - `type`: джерело походження (`'body' | 'query' | 'param' | 'custom'`);
    - `metatype`: тип TypeScript (наприклад, клас `CreateDishDto`);
    - `data`: ім'я переданого ключа (наприклад `'id'`).

---

### 6. Як працює декоратор `@Catch(HttpException)` у фільтрі виключень? Як за допомогою `host.switchToHttp()` отримати доступ до платформних об’єктів Express?
- **`@Catch(HttpException)`:** вказує IoC-контейнеру NestJS, які саме типи помилок повинен перехоплювати цей фільтр (у нашому випадку — всі помилки, що наслідують `HttpException`).
- **`host.switchToHttp()`:** NestJS є мультиплатформним фреймворком (підтримує HTTP REST, WebSockets, Microservices gRPC). Аргумент `ArgumentsHost` надає універсальний доступ до контексту, а виклик `.switchToHttp()` перемикає контекст у HTTP-режим, дозволяючи викликати:
  - `ctx.getRequest<Request>()` — для отримання URL, методу та IP;
  - `ctx.getResponse<Response>()` — для ручного встановлення статусу, заголовків та відправки JSON клієнту через `response.status().json()`.

---

### 7. Як створити зв’язку між `ValidationPipe` та бібліотекою `class-transformer` для коректної валідації вкладених об’єктів за допомогою `@ValidateNested()`?
Для коректної валідації вкладених об'єктів або масивів об'єктів необхідно:
1. Застосувати декоратор `@ValidateNested()` над полем вкладеного об'єкта.
2. Обов'язково застосувати декоратор `@Type(() => NestedClassDto)` з бібліотеки `class-transformer`.
   *Без декоратора `@Type()` компілятор не знає, на екземпляр якого саме класу трансформувати вхідний сирий JSON, і валідація вкладених полів буде проігнорована.*
3. У `main.ts` повинен бути увімкнений глобальний `ValidationPipe({ transform: true })`.

### 8. Яким чином оператор RxJS `tap()` в інтерцепторі дозволяє виконати дію над вихідним потоком відповіді, не змінюючи саме тіло даних?
- **Оператор `tap()`** у бібліотеці RxJS призначений виключно для виконання **побічних ефектів (side-effects)** без мутації значень потоку.
- Він «підглядає» за значеннями, які проходять крізь потік: коли метод контролера повертає результат, `tap()` перехоплює момент успішного завершення, дозволяє зафіксувати тривалість виконання, вивести запис у консоль та додати HTTP-заголовок через об'єкт `Response`, після чого без жодних змін транслює оригінальні дані відповіді далі до клієнта.
