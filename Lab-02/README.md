## 6. Відповіді на контрольні питання

### 1. Чим TypeScript відрізняється від JavaScript? Що відбувається з типами під час компіляції (транспіляції) у JavaScript?
- **TypeScript** є статично типізованою надмножиною мови JavaScript. Він додає статичний аналіз типів, інтерфейси, кортежі, дженеріки та розпізнавані об'єднання на етапі написання коду та компіляції.
- **Під час компіляції (транспіляції):** відбувається процес так званого **стирання типів (Type Erasure)**. Усі типи, інтерфейси, type aliases та перевірки TypeScript повністю видаляються. У скомпільований вихідний файл `.js` потрапляє виключно стандартний виконуваний код JavaScript. Типи не існують у runtime (під час виконання) і не сповільнюють роботу застосунку.

---

### 2. Які переваги надає прапорець `"strict": true` у файлі `tsconfig.json`? Що перевіряють правила `noImplicitAny` та `strictNullChecks`?
- **`"strict": true`** вмикає комплексний набір жорстких правил статичного аналізу, унеможливлюючи появу прихованих багів та непередбачуваної поведінки середовища виконання.
- **`noImplicitAny`**: забороняє компілятору неявно призначати тип `any` змінним або аргументам функцій, тип яких не вдалося автоматично вивести. Змушує розробника явно описувати типи.
- **`strictNullChecks`**: розділяє звичайні типи даних та значення `null` / `undefined`. Якщо змінна оголошена як `string`, вона не може приймати `null` чи бути `undefined`, поки це не буде явно дозволено через Union (`string | null`). Це ліквідує класичну помилку `TypeError: Cannot read property of undefined`.

---

### 3. У чому принципова різниця між типами `any` та `unknown`? Чому використання `unknown` вважається значно безпечнішим?
- **`any`** — повністю вимикає систему перевірки типів TypeScript. Змінній типу `any` можна призначити будь-яке значення, викликати в неї будь-які методи, звертатися до будь-яких властивостей без перевірки. Це «діра» в безпеці типу.
- **`unknown`** — є безпечним аналогом `any` (тип вищого порядку, top type). Змінна може містити будь-які дані, проте TypeScript **забороняє виконувати з нею будь-які операції**, доки розробник явно не звузить її тип (Type Narrowing за допомогою `typeof`, `instanceof` або Type Guard). Це захищає від виклику методів на невідповідних об'єктах.

---

### 4. Чим кортеж (tuple) у TypeScript відрізняється від звичайного масиву `Array<T>`?
- **Звичайний масив `Array<T>` (або `T[]`):** має довільну довжину, і всі його елементи мають один і той самий тип `T` (наприклад, `string[]`).
- **Кортеж (Tuple):** має **строго фіксовану кількість елементів**, де кожна позиція має свій визначений тип даних. Наприклад:
  ```typescript
  type GeoPoint = [latitude: number, longitude: number];
  ```
  Звернення за індексами `[0]` та `[1]` строго типізоване, а спроба додати третій елемент або переплутати порядок викликає помилку компілятора.

---

### 5. У чому полягає відмінність між типом-об’єднанням (`union type`) та типом-перетином (`intersection type`)? Наведіть приклади їх використання.
- **Тип-об'єднання (Union Type, `|`):** логічне «АБО». Значення може відповідати **одному з перелічених типів**.
  - *Приклад:* `type Status = 'pending' | 'delivered';` або `string | number`.
- **Тип-перетин (Intersection Type, `&`):** логічне «І». Об'єднує властивості кількох типів в один новий тип, вимагаючи, щоб об'єкт обов'язково містив **усі поля кожного з вихідних типів**.
  - *Приклад:*
    ```typescript
    type Order = OrderData & TimestampMetadata;
    ```
    Об'єкт типу `Order` зобов'язаний містити і поля замовлення (`orderId`, `items`), і часові мітки (`createdAt`, `updatedAt`).

---

### 6. Що таке розпізнаване об’єднання (discriminated union) і яку роль у ньому відіграє спільне літеральне поле-дискримінатор (discriminant property)?
- **Discriminated Union (Розпізнаване або марковане об'єднання):** це патерн проектування типів, у якому кожен варіант у Union містить одне спільне літеральне поле з унікальним значенням — **поле-дискримінатор**.
- **Роль поля-дискримінатора:** у конструкціях `switch (payment.type)` або `if (item.kind === 'card')` компілятор TypeScript автоматично розуміє, який саме тип даних знаходиться всередині гілки блоку, відкриваючи доступ до специфічних полів лише цього варіанта (наприклад, поля `cardNumber` та `cvv` для картки) і захищаючи від помилкового доступу до полів інших варіантів.

---

### 7. Що таке захисник типу (type guard)? Як оголошується функція-предикат із синтаксисом `value is TargetType`?
- **Type Guard (Захисник типу):** це спеціальна функція, яка під час виконання (runtime) перевіряє сутність і повідомляє компілятору TypeScript про її точний тип у разі повернення `true`.
- **Функція-предикат:** замість звичайного типу `boolean` у сигнатурі повернення вказується `parameterName is TargetType`:
  ```typescript
  export function isCreditCardPayment(payment: PaymentDetails): payment is CreditCardPayment {
    return payment.type === 'card';
  }
  ```
  Якщо `isCreditCardPayment(p)` повернула `true`, компілятор усередині блоку `if` автоматично звужує тип змінної `p` від загального `PaymentDetails` до точного `CreditCardPayment`.

---

### 8. Яке практичне призначення типу `never` у гілці `default` оператора `switch`? Як техніка `exhaustiveness checking` запобігає виникненню багів під час додавання нових типів у систему?
- **Призначення:** тип `never` представляє значення, яке ніколи не повинно настати. Якщо оброблено всі гілки об'єднання (усі значення дискримінатора), у блок `default` потрапляє порожній тип `never`.
- **Запобігання багам (Exhaustiveness checking):**
  ```typescript
  default: {
    const _exhaustiveCheck: never = payment;
    throw new Error(`Невідомий тип: ${_exhaustiveCheck}`);
  }
  ```
  Якщо у майбутньому інший розробник додасть у `PaymentDetails` новий спосіб оплати (наприклад, `CryptoPayment`), але забуде дописати для нього `case 'crypto'` у функції `processPayment`, компілятор TypeScript **відмовиться збирати проєкт** і видасть помилку:
  `Type 'CryptoPayment' is not assignable to type 'never'`.
  Це повністю виключає появу непокритих кейсів у продакшені.
