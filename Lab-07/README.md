## 4. Реалізація рівнів практичної роботи

### Рівень 1. Конфігурація Docker Compose та TypeORM
- У файлі `docker-compose.yml` описано сервіс `postgres` (образ `postgres:16-alpine`, порт `5432:5432`, БД `store_db`, користувач `nest_user`, збереження на іменований том `pgdata`). Відповідно до сучасного Compose Specification застарілу директиву `version` видалено.
- У `app.module.ts` конфігурація реалізована через `TypeOrmModule.forRootAsync`. Застосунок автоматично підключається до локального або Docker PostgreSQL 16, а за відсутності запущеного демона Docker прозоро використовує in-memory драйвер `pg-mem`, що забезпечує стабільне проходження тестів у будь-якому середовищі.
- Опції `autoLoadEntities: true` та `synchronize: true` забезпечують автоматичне виявлення сутностей і синхронізацію структури БД під час старту.

### Рівень 2. Персистентний CRUD через репозиторій
- У сервіс `DishesService` впроваджено `Repository<DishEntity>` через `@InjectRepository(DishEntity)`.
- Реалізовано методи:
  - `create(dto)`: створення сутності через `resourceRepo.create()` та збереження через `resourceRepo.save()`.
  - `findAll(query)`: отримання записів з сортуванням за спаданням дати створення (`createdAt: 'DESC'`).
  - `findOne(id)`: пошук за UUID через `resourceRepo.findOneBy({ id })`; при відсутності викидається `NotFoundException`.
  - `update(id, dto)`: перевірка наявності сутності, накладання оновлених полів та збереження через `resourceRepo.save()`.
  - `remove(id)`: перевірка наявності сутності та виклик операції видалення.

### Рівень 3. Offset-based пагінація, пошук та Soft Delete
- Створено клас `PaginationQueryDto` з полями `page` (дефолт 1), `limit` (дефолт 10), `search` (необов'язковий рядок пошуку).
- Метод `findAll` використовує `findAndCount({ skip, take, where, order })`:
  - `skip = (page - 1) * limit`
  - `take = limit`
  - `where: { title: ILike('%...%') }` при наявності пошукового запиту
  - Метод повертає уніфіковану відповідь із метаданими:
    ```json
    {
      "data": [ ... ],
      "meta": {
        "total": 5,
        "page": 1,
        "limit": 2,
        "totalPages": 3
      }
    }
    ```
- М'яке видалення (Soft Delete):
  - Метод `remove(id)` викликає `this.resourceRepo.softDelete(id)`. Запис не видаляється фізично, а лише отримує позначку дати у полі `deletedAt`. Усі наступні запити `find()` та `findAndCount()` автоматично ігнорують видалені записи завдяки вбудованому фільтру TypeORM (`deletedAt IS NULL`).
  - Додано ендпоінт `@Patch(':id/restore')`, який викликає `this.resourceRepo.restore(id)` і скидає `deletedAt` назад у `null`.

## 7. Відповіді на контрольні питання

### 1. Що таке ORM (Object-Relational Mapping)? Які переваги та потенційні недоліки має використання TypeORM порівняно з чистими SQL-запитами?
**Відповідь:**
- **ORM (Object-Relational Mapping)** — це технологія програмування, яка зв'язує несумісні моделі даних: об'єктно-орієнтовану модель мови програмування (класи TypeScript/JavaScript) та реляційну модель таблиць СКБД (рядки та стовпці SQL).
- **Переваги TypeORM:**
  - *Типобезпека та автодоповнення:* структури таблиць описані класами TypeScript, що унеможливлює помилки в назвах полів на етапі компіляції.
  - *Абстракція від діалекту СКБД:* зміна СУБД (наприклад, перехід з PostgreSQL на MySQL) потребує мінімальних змін конфігурації без переписування запитів.
  - *Захист від SQL Injection:* ORM автоматично параметризує всі значення в генерованих запитах.
  - *Автоматизація рутинних операцій:* наявність вбудованих механізмів міграцій, пагінації, аудиту (`@CreateDateColumn`, `@UpdateDateColumn`) та зв'язків між сутностями.
- **Недоліки TypeORM:**
  - *Накладні витрати продуктивності (overhead):* створення екземплярів об'єктів та додатковий рівень абстракції вимагають процесорного часу та пам'яті.
  - *Проблема N+1 запитів:* при недбалому завантаженні пов'язаних сутностей ORM може виконувати сотні зайвих запитів до БД.
  - *Складність нестандартних/аналітичних запитів:* для побудови складних агрегацій та віконних функцій чистий SQL або QueryBuilder є значно ефективнішим та прозорішим.

### 2. Чому параметр конфігурації `synchronize: true` дозволяється використовувати виключно на етапі розробки і суворо заборонений у виробничому середовищі (production)?
**Відповідь:**
Опція `synchronize: true` під час кожного запуску додатку порівнює класи сутностей TypeScript зі схемою бази даних і автоматично виконує DDL-запити (`ALTER TABLE`, `DROP COLUMN`, `DROP TABLE`).
- **Чому це небезпечно в продакшені:**
  - Якщо поле сутності перейменовано або видалено з коду, TypeORM виконає `ALTER TABLE DROP COLUMN`, що призведе до **незворотної втрати даних користувачів**.
  - Зміна типу колонки може викликати невдалу конвертацію та падіння процесу під навантаженням.
  - У кластері з кількома репліками бекенду одночасна синхронізація схеми викликає блокування таблиць (deadlock).
- **Як діяти в продакшені:** параметр `synchronize` вимикається (`synchronize: false`), а будь-які зміни схеми бази даних вносяться контрольовано через **файли міграцій (TypeORM Migrations)**, які попередньо тестуються на staging-середовищі та фіксуються в системі контролю версій Git.

### 3. Чим відрізняється первинний ключ на основі автоінкрементного цілого числа (increment) від універсального унікального ідентифікатора (UUID)? Які переваги надає UUID у розподілених системах?
**Відповідь:**
- **Автоінкремент (`increment / SERIAL`):**
  - Це послідовне ціле число (1, 2, 3...), яке генерується централізовано лічильником бази даних (`sequence`).
  - *Мінуси:* уразливість до перебору (enumeration attack — зловмисник може легко перебрати всі ID: `/dishes/1`, `/dishes/2`), а також неможливість згенерувати ID до моменту успішного запису рядка в базу.
- **UUID (Universally Unique Identifier, v4):**
  - 128-бітне число, що записується у вигляді 36 символів шістнадцяткового рядка (наприклад, `5c45ea8f-fa3b-4967-b586-cc122e9b5ff7`), що базується на криптографічно стійкій випадковості.
- **Переваги UUID у розподілених системах:**
  1. *Децентралізована генерація:* будь-який сервіс, мікросервіс або клієнтський застосунок може згенерувати гарантовано унікальний ідентифікатор автономно без звернення до БД.
  2. *Безпека від зливу бізнес-метрик:* конкуренти не можуть визначити обсяги продажів або кількість користувачів за різницею номерів ID.
  3. *Простота шардингу та реплікації:* злиття даних з різних баз або серверів не призводить до колізій первинних ключів.

### 4. Які базові методи надає клас `Repository<T>` у TypeORM для вибірки, збереження, оновлення та видалення записів?
**Відповідь:**
Клас `Repository<T>` реалізує шаблон Repository і надає такі базові методи:
1. **Створення екземпляра:**
   - `create(dto)` — створює новий інстанс сутності в пам'яті (без запису в БД).
2. **Збереження та оновлення:**
   - `save(entity | entities)` — зберігає одну або кілька сутностей. Якщо первинний ключ відсутній — виконує `INSERT`; якщо присутній — виконує `UPDATE`.
   - `update(criteria, partialEntity)` — виконує прямий SQL `UPDATE` за критерієм без завантаження сутності в пам'ять.
3. **Вибірка:**
   - `find(options)` — повертає масив сутностей, що задовольняють умови пошуку.
   - `findOne(options)` та `findOneBy(where)` — повертає першу сутність або `null`.
   - `findAndCount(options)` — повертає кортеж `[items, totalCount]`.
4. **Видалення:**
   - `delete(criteria)` — прямий SQL `DELETE` за критерієм/ID.
   - `remove(entity)` — фізичне видалення конкретного об'єкта сутності з викликом життєвих хуків (`@BeforeRemove`, `@AfterRemove`).
   - `softDelete(criteria)` — м'яке видалення (запис дати в `@DeleteDateColumn`).
   - `restore(criteria)` — відновлення м'яко видаленого запису (скидання колонки в `null`).

### 5. У чому полягає відмінність між методами `delete()` та `remove()` у репозиторії TypeORM?
**Відповідь:**
- **`delete(id | criteria)`:**
  - Приймає ідентифікатор або критерій (наприклад, `{ id }`).
  - Формує і відправляє один прямий SQL-запит: `DELETE FROM dishes WHERE id = $1`.
  - **Не завантажує** сутність у пам'ять додатка.
  - **Не викликає** entity lifecycle hooks (`@BeforeRemove`, `@AfterRemove`) та підписників (`EntitySubscribers`).
  - Працює значно швидше при масовому видаленні.
- **`remove(entity)`:**
  - Приймає **повний об'єкт сутності** (який попередньо необхідно завантажити з БД через `findOneBy`).
  - Виконує видалення конкретного екземпляра.
  - **Викликає всі життєві хуки та підписники** (наприклад, логування аудиту, каскадне видалення зв'язаних файлів тощо).
  - Потребує додаткового запиту `SELECT` для попереднього завантаження сутності.

### 6. Як влаштований механізм м’якого видалення (Soft Delete)? Які переваги надає колонка `@DeleteDateColumn()` для збереження аудиторського сліду?
**Відповідь:**
- **Влаштування Soft Delete:**
  - У таблицю додається стовпець `deletedAt` типу `timestamp with time zone`, помічений декоратором `@DeleteDateColumn()`.
  - Замість виконання руйнівного запиту `DELETE FROM`, виклик `softDelete(id)` генерує `UPDATE dishes SET "deletedAt" = CURRENT_TIMESTAMP WHERE id = $1`.
  - TypeORM на рівні ядра модифікує всі стандартні запити вибірки (`find`, `findOne`, `findAndCount`), автоматично додаючи предикат `WHERE deletedAt IS NULL`.
- **Переваги для аудиторського сліду:**
  1. *Збереження історії:* дані ніколи не втрачаються безповоротно; зберігається точний час вилучення запису з експлуатації.
  2. *Цілісність зв'язків:* замовлення, чеки та аналітика, що посилаються на видалену страву, не порушують обмеження зовнішніх ключів (`FOREIGN KEY`).
  3. *Можливість швидкого відновлення:* якщо адміністратор або клієнт видалив запис помилково, його можна миттєво відновити методом `restore(id)` без підняття бекапів бази даних.

### 7. Як працює пагінація за допомогою параметрів `skip` та `take`? Як вирахувати зміщення `skip` для довільного номера сторінки `page` та розміру вибірки `limit`?
**Відповідь:**
Пагінація зі зміщенням (offset-based pagination) у реляційних БД транслюється у конструкцію SQL:
`SELECT * FROM dishes ORDER BY "createdAt" DESC LIMIT <take> OFFSET <skip>;`
- `take` (або `limit`) — максимальна кількість рядків, яку СКБД повинна повернути в поточному запиті.
- `skip` (або `offset`) — кількість рядків від початку відсортованої вибірки, яку СКБД повинна пропустити.
- **Формула розрахунку зміщення:**
  $$\text{skip} = (\text{page} - 1) \times \text{limit}$$
  - Якщо `page = 1`, `limit = 10` $\rightarrow \text{skip} = (1 - 1) \times 10 = 0$ (вибираються рядки з 1 по 10).
  - Якщо `page = 2`, `limit = 10` $\rightarrow \text{skip} = (2 - 1) \times 10 = 10$ (пропускаються перші 10 рядків, вибираються 11–20).
  - Якщо `page = 3`, `limit = 2` $\rightarrow \text{skip} = (3 - 1) \times 2 = 4$.
- **Загальна кількість сторінок:**
  $$\text{totalPages} = \lceil \frac{\text{total}}{\text{limit}} \rceil = \text{Math.ceil}(\text{total} / \text{limit})$$

### 8. Що робить метод `findAndCount()` у TypeORM та чому він є більш оптимальним для реалізації пагінації, ніж окремі виклики `find()` та `count()`?
**Відповідь:**
- **Що робить `findAndCount()`:**
  - Метод приймає ті самі параметри, що й `find()` (умови `where`, пагінацію `skip`/`take`, сортування `order`), та повертає кортеж із двох елементів: `[items, totalCount]`, де `items` — масив сутностей поточної сторінки (обмежений `take`), а `totalCount` — загальна кількість усіх рядків, що задовольняють умову `where` (без врахування обмеження `skip`/`take`).
- **Чому це більш оптимально:**
  1. *Консистентність та атомарність параметрів:* умови фільтрації (`where`), зв'язки (`relations`) та специфікації описуються в одному об'єкті конфігурації один раз, що виключає ризик розсинхронізації умов між вибіркою та підрахунком.
  2. *Оптимізація запитів:* TypeORM виконує ці запити в межах єдиного підключення або паралельного батчингу, мінімізуючи накладні витрати мережевого round-trip.
  3. *Чистота коду:* замість двох окремих асинхронних викликів `const items = await repo.find(...)` та `const total = await repo.count(...)`, розробник використовує одну ідіоматичну конструкцію `const [items, total] = await repo.findAndCount(...)`.
