## 1. Мета роботи
- Опанувати розширені засоби мови TypeScript, критично необхідні для промислової розробки серверних застосунків на базі NestJS: узагальнення (generics), утилітарні типи (utility types) та метапрограмування на основі декораторів (decorators).
- Навчитися проєктувати типізовані архітектурні патерни, зокрема патерн репозиторію (Generic Repository Pattern) та універсальні обгортки API-відповідей (`ApiResponse<TData>`).
- Опанувати трансформацію типів для створення об’єктів передачі даних (DTO) за допомогою `Omit<T, K>`, `Partial<T>`, `Pick<T, K>` та `Record<K, V>`.
- Створити власні декоратори класів (`@FrozenEntity()`) та методів (`@LogExecutionTime()`) з використанням дескрипторів властивостей (`PropertyDescriptor`), налаштувати компілятор для підтримки метаданих та організувати чисту модульну структуру за допомогою barrel files.

## 4. Опис реалізації за рівнями

### Рівень 1. Базовий: generic-інтерфейси та Generic In-Memory Repository
1. **Налаштування компілятора (`tsconfig.json`)**:
   Увімкнено обов'язкові прапорці експериментального метапрограмування:
   ```json
   {
     "compilerOptions": {
       "experimentalDecorators": true,
       "emitDecoratorMetadata": true
     }
   }
   ```
2. **Базові Generic-типи**:
   - `BaseEntity`: містить обов'язкові системні поля `id: string`, `createdAt: Date`, `updatedAt: Date`.
   - `ApiResponse<TData>`: універсальний контейнер відповіді бекенд-сервера, що огортає довільні корисні дані `data: TData`, часову мітку `timestamp: Date` та метадані пагінації/версії `meta?: Record<string, unknown>`.
3. **Generic Repository Pattern**:
   - Створено інтерфейс-контракт `IRepository<T extends BaseEntity>`, який обмежує тип сутності наявністю системних полів (`T extends BaseEntity`).
   - Реалізовано узагальнений клас `InMemoryRepository<T extends BaseEntity>`, який інкапсулює колекцію сутностей у масиві `protected items: T[] = []` та реалізує методи `create`, `findById`, `findAll`, `deleteById`.

---

### Рівень 2. Трансформація типів (Utility Types) та DTO
1. **Статуси життєвого циклу через `enum`**:
   ```typescript
   export enum EntityStatus {
     Active = 'ACTIVE',
     Archived = 'ARCHIVED',
     Draft = 'DRAFT',
   }
   ```
2. **Генерація DTO за допомогою утилітарних типів**:
   - `CreateDto<T>`: за допомогою `Omit<T, 'id' | 'createdAt' | 'updatedAt'>` відсікаються системні поля, що автоматично генеруються сервером при створенні.
   - `UpdateDto<T>`: за допомогою `Partial<CreateDto<T>>` усі поля стають опціональними (`?`), дозволяючи клієнту оновлювати лише потрібну підмножину даних у PATCH-запитах.
   - `EntitySummary<T>`: за допомогою `Pick<T, 'id' | 'title' | 'price'>` створюється оптимізований легкий зріз полів сутності.
   - `EntityAnalytics`: типізується через `Record<EntityStatus, number>`, гарантуючи наявність лічильника для кожного з можливих статусів.
3. **Операція оновлення в репозиторії**:
   Реалізовано метод `update(id: string, patch: UpdateDto<T>): T | null`, який актуалізує дату `updatedAt: new Date()` та зберігає абсолютну незмінність первинного ключа `id`.

---

### Рівень 3. Просунутий: Метапрограмування та архітектурна модульність
1. **Декоратор методу `@LogExecutionTime()`**:
   - Фабрика декоратора перехоплює дескриптор цільового методу (`PropertyDescriptor`).
   - За допомогою `performance.now()` фіксує точний час до та після виклику оригінального методу.
   - Логує бенчмарк у мілісекундах: `[BENCHMARK] Метод <MethodName> виконано за <Time> ms.`
2. **Декоратор класу `@FrozenEntity()`**:
   - Викликає `Object.freeze()` на функції-конструкторі та його прототипі.
   - Забезпечує захист від модифікації класу в runtime (Runtime Tamper Protection).
3. **Предметний репозиторій `FoodRepository`**:
   - Усі методи (`create`, `update`, `findAll`) позначені декоратором `@LogExecutionTime()`.
4. **Централізований реекспорт (Barrel Files)**:
   - Вхідна точка `src/index.ts` імпортує типи та класи виключно з папок `./types/index.js`, `./repositories/index.js`, не прив'язуючись до глибоких внутрішніх файлів.

## 6. Відповіді на контрольні питання

### 1. Що таке параметри типу (generics) у TypeScript? Яку проблему вони вирішують порівняно з використанням типу `any` або `unknown`?
- **Дженерики (Generics)** — це механізм створення узагальнених компонентів (функцій, класів, інтерфейсів), які можуть працювати з різними типами даних, зберігаючи повну статичну типізацію та зв'язок між аргументами й результатом повернення.
- **Проблема, яку вони вирішують:**
  - Якщо використати `any`, TypeScript повністю вимикає перевірку типів, втрачається автодоповнення в IDE та виникає ризик прихованих помилок.
  - Якщо використати `unknown`, тип безпечний, але вимагає громіздкого ручного тайп-чекінгу перед кожною дією.
  - **Дженерик `<T>`** динамічно підставляє конкретний тип при виклику: компілятор знає, що якщо ми передали в `create(item: FoodEntity)`, то назад отримаємо саме `FoodEntity` з усіма його властивостями.

---

### 2. Як працює обмеження узагальнень (type constraints) за допомогою ключового слова `extends`? Наведіть приклад.
- **Обмеження типу (Type Constraint)** через `extends` звужує множину допустимих типів для дженерика, гарантуючи, що переданий тип обов'язково містить визначені поля або реалізує конкретний інтерфейс.
- **Приклад:**
  ```typescript
  interface BaseEntity {
    id: string;
  }

  function getEntityId<T extends BaseEntity>(entity: T): string {
    return entity.id; // Безпечно! Компілятор точно знає, що id існує в T
  }
  ```
  Якщо передати тип, у якого немає поля `id: string`, TypeScript видасть помилку на етапі компіляції.

---

### 3. У чому полягає різниця між утилітарними типами `Omit<T, K>` та `Pick<T, K>`? У яких практичних сценаріях застосовується кожен із них?
- **`Pick<T, K>`** — конструює новий тип, **вибираючи лише вказаний набір ключів `K`** з вихідного типу `T`.
  - *Сценарій:* формування легковажних моделей передачі даних (наприклад, `EntitySummary` для короткого списку товарів у мобільному застосунку, де потрібні лише `id`, `title`, `price`).
- **`Omit<T, K>`** — конструює новий тип, **видаляючи вказаний набір ключів `K`** з вихідного типу `T`.
  - *Сценарій:* створення DTO для додавання сутності (`CreateDto`), коли нам потрібні всі поля сутності, **крім** системних полів (`id`, `createdAt`, `updatedAt`), які генерує база даних.

---

### 4. Для чого призначений утилітарний тип `Partial<T>`? Чому він є фундаментальним під час створення DTO для операцій оновлення (PATCH)?
- **Призначення:** `Partial<T>` обходить усі поля типу `T` і робить кожне з них **опціональним** (додає знак `?`).
- **Значення для PATCH-запитів:**
  - Згідно зі стандартом HTTP REST, метод `PATCH` призначений для **часткового оновлення** ресурсу. Клієнт не зобов'язаний надсилати весь об'єкт, а передає лише те поле, яке змінилося (наприклад, лише нову ціну `{ price: 395 }`).
  - `UpdateDto<T> = Partial<CreateDto<T>>` гарантує, що клієнт може передати будь-яку комбінацію полів або лише одне поле, і тип залишатиметься повністю валідним для TypeScript.

---

### 5. Як працює утиліта `Record<K, V>`? Які типи даних дозволено передавати як перший аргумент `K`?
- **Як працює:** `Record<K, V>` створює типізовану словникову структуру (асоціативний масив / карту об'єкта), де кожен ключ має тип `K`, а кожне значення — тип `V`.
- **Допустимі типи для `K`:** як перший параметр дозволено передавати лише типи, сумісні з ключами об'єктів JavaScript (`K extends keyof any`, тобто `string | number | symbol`), або їх об'єднання (Union літералів, `enum`).
- *Приклад з роботи:* `Record<EntityStatus, number>` гарантує, що об'єкт аналітики статусів містить строго ключі `'ACTIVE'`, `'ARCHIVED'`, `'DRAFT'`, а значеннями є числа `number`.

### 6. Що таке декоратор у TypeScript? Які обов’язкові параметри конфігурації у файлі `tsconfig.json` необхідні для підтримки експериментальних декораторів?
- **Декоратор** — це спеціальний патерн метапрограмування, функція вищого порядку, яка застосовується до класу, методу, властивості або параметра та дозволяє додавати метадані, модифікувати або перехоплювати їхню поведінку без зміни вихідного коду самої функції.
- **Обов'язкові прапорці в `tsconfig.json`:**
  ```json
  {
    "compilerOptions": {
      "experimentalDecorators": true,
      "emitDecoratorMetadata": true
    }
  }
  ```

---

### 7. Що являє собою об’єкт `PropertyDescriptor` у декораторі методу? Як за допомогою властивості `descriptor.value` перехопити та підмінити виконання оригінального методу?
- **`PropertyDescriptor`** — це стандартний об'єкт JavaScript, який описує характеристики властивості об'єкта (`value`, `writable`, `enumerable`, `configurable`). Для методів властивість `descriptor.value` зберігає саму функцію методу.
- **Як перехопити метод:**
  1. Зберігаємо посилання на вихідний метод:
     ```typescript
     const originalMethod = descriptor.value;
     ```
  2. Замінюємо `descriptor.value` на власну функцію-обгортку:
     ```typescript
     descriptor.value = function (...args: unknown[]) {
       // Логіка до виклику (старт таймера, валідація тощо)
       const result = originalMethod.apply(this, args);
       // Логіка після виклику (зупинка таймера, логування результату)
       return result;
     };
     ```
  3. Повертаємо змінений `descriptor`.

### 8. Що таке архітектурний патерн Barrel File? Які переваги він надає під час масштабування кодової бази бекенд-застосунку?
- **Barrel File** — це файл (зазвичай з назвою `index.ts`), розташований у корені підкаталогу модуля, який збирає та централізовано реекспортує публічний інтерфейс (типи, класи, інтерфейси, сервіси) цього каталогу:
  ```typescript
  export * from './base.types.js';
  export * from './food.types.js';
  ```
- **Переваги:**
  1. **Інкапсуляція:** приховує внутрішню файлову структуру модуля. Клієнтський код імпортує все з одного місця (`import { FoodEntity } from './repositories'`).
  2. **Легкий рефакторинг:** переміщення або перейменування файлів усередині модуля не ламає зовнішні імпорти в усьому проєкті — достатньо змінити шлях лише в одному Barrel File.
  3. **Чистота коду:** ліквідує довгі спагеті-шляхи імпортів (`../../../../repositories/impl/food.repository`).
